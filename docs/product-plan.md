# TabCarry：产品方案与开发计划

日期：2026-09-24。状态：1.0.0 已实现；下文保留原始范围和后续路线。本次完成官方资料调研，未安装竞品或做用户访谈。下文竞品事实与我们的设计判断分开说明。

## 1. 产品判断

值得做，先作为每天自己会用的小工具。核心承诺：**把现在打开的一组页面存下来，下次按需要继续。**

差异放在操作清楚、界面安静、数据可信。纯本地与一键保存已经有同类产品提供，不能单独当作独有卖点。先通过自用验证“比现有工具少几次点击、少一点犹豫”，再考虑推广。

TabCarry 已由用户确认；GitHub 仓库和本地目录均使用 tabcarry。名称查重见 naming-check.md。

与 NotBadBookmark 的分工：书签管理长期收藏；TabCarry 保存某一时刻的工作上下文。保持两个独立产品和数据存储，暂不互相同步或合并。

## 2. 同类产品观察

| 产品                                                                             | 官方资料可确认的方向                                                         | 对本项目的启发                                                     |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| [Session Buddy](https://sessionbuddy.com/docs/)                                  | 有会话集合、历史、导入导出和备份恢复等完整工作流                             | 学习恢复可靠性与错误说明；我们的首页保持简短，不把历史管理放到中心 |
| [Tab Session Manager（sienori）](https://github.com/sienori/Tab-Session-Manager) | 保存和恢复窗口、标签页，支持自动保存                                         | 手动快照与自动记录要明确分开，避免列表被自动记录占满               |
| [OneTab](https://www.one-tab.com/)                                               | 把打开的标签收成列表，支持单个或全部恢复；目前也宣传文件夹、笔记和同步等功能 | 学习快速收起的明确动作；我们的普通“保存”默认不关闭页面             |
| [Toby](https://www.gettoby.com/)                                                 | 项目空间、集合、搜索、协作和跨设备同步                                       | 学习清晰的内容层级；当前需求没有团队空间和账户的必要               |

这里不把“竞品 UI 差”当作已验证事实。用户觉得不够简洁是本项目起点；应在原型和真实使用中验证改善程度，而不是只换一套颜色。

另一个替代方案是浏览器自身的恢复机制。应在开发第一阶段实际对照当前 Chrome 的继续浏览、最近关闭和标签组体验：我们要提供的是可命名、可反复恢复、可选择部分页面的长期快照。

## 3. 三个主要场景

1. 下班：保存全部普通窗口，第二天按原来的窗口和分组继续。
2. 临时切换：保存当前窗口，去做其他事；回来追加打开或另开窗口。
3. 调研回访：搜索昨天的某个页面，只打开其中两个标签，不必恢复整个会话。

默认保存所有普通窗口，按钮直接显示“保存全部 · 3 个窗口 · 28 个标签”；菜单提供当前窗口与选中标签，记住用户上次选择。一次点击即保存，以日期时间自动命名；保存后允许就地改名，不让命名成为必填步骤。

首次启用时简要说明保存范围。无痕窗口在第一版排除；不跨 Chrome 用户配置收集数据。扩展自身管理页默认排除，跳过数量与原因可查看。

## 4. 第一版功能范围

| 功能     | 明确行为                                                                         |
| -------- | -------------------------------------------------------------------------------- |
| 保存     | 全部普通窗口、当前窗口、选中标签；成功提示以本地事务提交完成为准                 |
| 快照内容 | 原始 URL、标题、顺序、窗口归属、固定标签、活动标签；原生分组名称、颜色、折叠状态 |
| 查找     | 会话名称、页面标题、URL；结果显示所属会话和窗口，可直接打开单项                  |
| 管理     | 重命名、收藏置顶、删除、撤销；回收站拟保留 30 天，可主动清空                     |
| 恢复     | 按原窗口结构新建窗口；追加到当前窗口；只恢复选中的窗口/分组/标签                 |
| 备份     | 带格式版本的 JSON 导入导出，完整保留层级；导入预览并验证后写入                   |
| 外观     | 浅色、深色、跟随系统；键盘操作；中英文本地化                                     |

“保存并关闭”可在第一版后半段实现为独立菜单动作：先保存、确认已落盘，再核对捕获的 tab ID 与当前 URL，关闭仍匹配的标签。新打开或已导航的标签保留并说明。明确提醒不能保存未提交的网页输入；保存失败绝不关闭。不可把这个动作混入默认保存按钮。

第一版默认不自动删除保存记录，不在恢复后删除快照；“保存”与“再次打开”都可以重复使用。

### 恢复方式必须说清楚

| 界面文案         | 实际操作                                                               | 默认值             |
| ---------------- | ---------------------------------------------------------------------- | ------------------ |
| 按原窗口打开     | 每个保存窗口新建一个窗口，恢复内部结构                                 | 整个会话的主要按钮 |
| 添加到当前窗口   | 所选页面在调用时捕获的目标窗口追加；多个保存窗口合并，保留可恢复的分组 | 菜单选项           |
| 在新标签页打开   | 单个页面在目标窗口新增标签；Ctrl/Cmd 点击支持后台打开                  | 单项主要行为       |
| 在当前标签页打开 | 单项替换调用时的活动标签；明确动作，不以含糊的“打开”表示               | 单项菜单选项       |
| 替换当前窗口     | 先保存现场再关闭旧标签，属于更复杂的切换动作                           | 后续版本，首版不做 |

管理页自身是一个扩展标签，不能把它误认为用户希望替换的网页。点击扩展图标时记录来源窗口和标签；目标已关闭则提示选择新窗口，不悄悄覆盖另一个页面。

默认保留重复 URL，因为同网址可能承担不同任务。提供“跳过目标窗口里已打开的网址”开关，显示跳过数量；按完整 URL 比较，不擅自删除查询参数或 fragment。新窗口完整恢复默认关闭去重，避免损坏原始结构。

超过 50 个待打开标签时显示一次简短确认（阈值待自测调整）。逐批创建、可停止后续任务，已打开的标签保留；失败显示具体页面并允许只重试明确失败项。区分“浏览器已创建标签”与“网页成功加载”，不把登录失效或站点离线误报成恢复成功。

## 5. UI 方案

### 快捷弹窗

约 380px 宽，默认只呈现：当前保存范围与数量、一个保存按钮、最近 5 个会话、打开管理页。保存选项通过按钮旁的小菜单展开。弹窗关闭后保存和恢复任务仍由后台继续执行。

### 完整管理页

桌面采用两栏：左侧约 280px 为会话列表，右侧为当前会话详情。顶部搜索固定可见；列表仅有名称、时间、窗口/标签数量、收藏状态。详情按窗口和标签组展开，网页标题为主、域名为辅。

示意布局：

```text
TabCarry                         搜索会话或页面     保存全部 ▾
───────────────────────────────────────────────────────────────
已保存   收藏   回收站       产品调研                  按原窗口打开 ▾
                            今天 18:42 · 2 个窗口 · 18 个标签
产品调研   18 tabs          □ 窗口 1 · 10 tabs
周末旅行    7 tabs             □ 分组：参考资料
发布准备   12 tabs               页面标题                   域名
                               页面标题                   域名
                            □ 窗口 2 · 8 tabs
```

窄窗口进入列表 → 详情模式，有明确返回入口，不挤成三列。首页空状态只讲“保存打开的页面，下次继续”，给出立即保存按钮，不塞教学轮播。

配色起点：浅色冷灰背景 #F7F8FA、白色内容面板、深灰文字 #202733、蓝色主操作 #315CCD；深色背景 #171A20、面板 #20252D、浅色文字 #E8EDF3、柔和蓝色 #9BB8FF。以上为待验证设计值，开发时检查正文及交互状态对比度。颜色只表达主操作、选中与错误；少用大面积色块、渐变和阴影。

标签行约 40–44px 高，标题单行截断，完整 URL 可查看和复制；控件在键盘焦点与触摸设备上同样可发现，不能只靠 hover。保存、恢复进度和错误使用原位状态提示，错误保留到用户处理。

第一版使用随包图标和域名首字母。列表不请求 Google favicon 或远程图片，避免用户仅浏览保存记录就产生外部访问。

## 6. 值得做的扩展功能

按价值排序，第一版后用真实使用验证：

1. **轻量自动快照**：显式开启，独立“最近活动”区域；仅有变化才记录，先拟最近 30 份/7 天，手动快照不参与淘汰。处理 Chrome 启动恢复期间的瞬时空状态，保留上一轮有效快照。
2. **更新已有会话**：当前工作持续推进时更新同一个会话，保留有限历史版本，解决“调研 1、调研 2、最终版”的堆积。
3. **快捷键保存和快速查找**：操作步骤更少，快捷键可配置并避免抢占浏览器常用键。
4. **缺失页面恢复**：比较保存内容与目标窗口，只补开未打开的页面；展示比较结果，避免错过有意重复的标签。
5. **选择式迁移**：先支持 OneTab 风格的 URL 文本导入；有用户需求后再适配竞品 JSON，按实际导出样本测试，不能假设格式恒定。
6. **轻量整理**：短备注、域名筛选、会话合并。标签体系、复杂文件夹等有明确使用需求再加。
7. **大规模恢复优化**：评估分批加载或本地占位页。占位页影响地址栏、标题和崩溃恢复，不能未经验证当作“原生懒加载”。

暂不安排：AI 分类、云同步、登录、团队协作、网页全文/截图、替换新标签页、跨浏览器同步、付费墙。先保持免费自用工具的清晰范围。

## 7. 技术方案和边界

建议 Manifest V3 + TypeScript + React + Vite。会话存 IndexedDB，偏好存 chrome.storage.local；不用 storage.sync、远程服务或遥测。选择熟悉的技术栈减少维护成本，不复制 NotBadBookmark 的书签业务模型。

Chrome 的 `sessions` API 主要提供最近关闭和设备会话，返回列表上限为 25，不是长期命名快照数据库。本产品需自己保存 URL 与结构；第一版无需申请 sessions 权限。[官方说明](https://developer.chrome.com/docs/extensions/reference/api/sessions)

拟申请 `tabs`（读取全部标签的标题、URL）、`tabGroups`（分组元数据）、`storage`（本地偏好）。不申请 history、cookies、scripting 或全站 host permissions；自动快照阶段再加入 alarms。activeTab 仅覆盖当前页临时访问，不足以读取全部窗口的内容。[Tabs 权限](https://developer.chrome.com/docs/extensions/reference/api/tabs)

分组 ID 只在浏览器会话内唯一；保存时改用自有稳定 ID，恢复时建立新旧映射，不能把旧 tab/window/group ID 当作持久标识。共享组仅恢复为普通本地组，不承诺共享关系。[Tab Groups](https://developer.chrome.com/docs/extensions/reference/api/tabGroups)

chrome.storage.local 存储不是独立备份，卸载扩展会清除其数据；storage.session 会随重启等事件清空。核心持久记录用 IndexedDB 事务，配额不足必须明确失败；任何存储位置都需要可导出的独立备份。[Storage](https://developer.chrome.com/docs/extensions/reference/api/storage)

MV3 后台会休眠，内存变量不能作为保存成功或恢复进度的唯一依据。后台统一接收变更请求，操作队列和逐项状态写入本地。重启后区分未开始、已完成、失败和结果不确定，结果不确定时先核对，不能自动重复打开。[生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)

根据上述 API 范围，本方案仅重建页面入口和浏览器结构：不采集或恢复 cookies、登录令牌、表单输入、前进后退历史、滚动位置、视频进度或完整离线网页。已有登录能否继续由浏览器和网站决定。离线可以保存/管理已有标题和 URL，但重新加载网站仍可能需要联网。

HTTP/HTTPS 是第一版可靠支持范围。内部 chrome://、file://、其他扩展页分别识别并保留可显示信息；对不可恢复项给出原因和复制 URL，不能静默丢失。javascript:/data:/blob: 不自动执行或恢复；无有效 URL 的记录明确标记。保存中的导航优先级（pendingUrl 与已提交 URL）需在技术验证中统一，避免保存出旧标题配新 URL。

窗口尺寸、多显示器位置、分屏、画中画、DevTools 等不承诺精确还原；第一版保留窗口划分，几何位置由 Chrome 合理放置。

### 数据模型草案

```text
Session: id, schemaVersion, name, createdAt, updatedAt, source,
         favorite, deletedAt, revision, windows[]
Window:  id, order, focused, tabs[], groups[]
Tab:     id, url, title, order, pinned, active, groupRef?, restoreSupport
Group:   id, title, color, collapsed
RestoreJob: id, sessionId, sessionRevision, target, options, items[], status
```

快照采用一次事务写入；UI 收到提交确认才提示成功。重命名和删除使用 revision 冲突检查，多个管理页面保持同步。恢复以开始时固定的快照版本执行，中途编辑不改变正在执行的任务。

导出格式独立版本化，不导出旧浏览器运行时 ID。导入验证大小、层级、字段、URL 和计数，显示预览；第一版拟限 25MB/50,000 条 URL，作为防护阈值而非性能承诺。重复导入依照备份 ID 和内容判断，冲突提示另存副本，不覆盖用户现有数据。

## 8. 分三轮交付

工期是单人开发的粗估，取决于原生 Chrome 验证；不是已承诺完成日期。

| 轮次        | 预计                       | 交付物                                                             | 通过标准                                                                             |
| ----------- | -------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| 1：核心闭环 | 2–3 天                     | 可加载扩展、快捷弹窗、手动保存、多窗口/组恢复、基础管理页          | 自用数据经重启仍在；已保存结构可恢复；默认保存和恢复不关闭任何现有标签               |
| 2：完整可用 | 3–4 天                     | 搜索、选择恢复、重命名/收藏、回收站、JSON 备份、浅深色和键盘细节   | 损坏导入不改变已有数据；备份往返一致；失败显示具体条目；连续操作不重复写入           |
| 3：打磨发布 | 2–3 天开发 + 至少 7 天自用 | 大会话测试、休眠恢复、视觉打磨、中英文本、隐私页面、商店素材和 ZIP | 真实 Chrome 验收完成、恢复结果可核对、无未解释的数据丢失；新用户能自行完成保存和恢复 |

自动快照、更新已有会话等进入后续版本，不为首版拖长范围。第一轮优先证明数据闭环，第二轮再细修布局和颜色。

## 9. 验证清单

- 普通场景：1/3/10 个窗口，10/100/500 个标签；混合固定标签、多个分组、中文长标题、重复网址、空名称。
- 保存过程中标签导航/关闭，目标窗口在恢复前消失，恢复中拖动标签、关闭管理页、后台休眠、Chrome 重启。
- 连续双击、两个管理页同时重命名/删除、恢复中编辑快照、导入中断、数据迁移失败、存储写入失败。
- 非法/不支持 URL、离线、file 访问未授权、无痕排除、重新安装后从 JSON 备份恢复。
- 导出 → 导入之后，URL、顺序、窗口和分组元数据逐项相等；迁移有旧格式样本。
- 浅深色、键盘完整流程、200% 缩放、窄窗口、减少动态效果、长列表性能。
- “已创建”数量 + “跳过”数量 + “失败”数量可与请求总数对齐；未知结果独立显示。
- 自用观察：一次保存是否顺畅、找旧会话是否容易、恢复目标是否清楚、是否产生冗余快照。公开前请 3–5 人尝试，不加入后台行为追踪。

## 10. 完成状态与下一步

1.0.0 已完成三轮开发并通过自动化与隔离 Chrome for Testing 原生 API 验收，详见 validation.md。尚未上传 Chrome Web Store，尚未进行规划中的 7 天日常使用观察。自动快照、更新已有会话等仍是后续功能。

产品网站和隐私页已在本仓库 docs/site 中实现，通过 GitHub Actions 构建发布至 https://xnu.app/tabcarry/ 和 https://xnu.app/tabcarry/privacy/ 。官网以 Chrome Web Store 安装为入口，目前标注即将上线。产品规划 Markdown 不应被直接当作对外功能承诺。

### 本轮整体复查与优先级

- 已处理：回收站清理与恢复的并发风险、恢复中标签组跨窗口移动的保护、弹窗无障碍名称和关闭按钮语言。31 项测试及隔离 Chrome 实测通过。
- 发布前：完成商店提交，以及连续自用，重点记录保存是否重复、能否找回工作会话、恢复目标是否清晰。当前仍未上架。
- 下一版本优先候选：显式“更新已有会话”，须保留旧版本或可撤销，不能直接覆盖唯一快照。先观察真实使用频率再决定。
- 第二优先级：本地定时快照与备份提醒，需要明确保留数量和清理规则，避免会话列表膨胀。
- 暂缓：云同步、账户、AI、复杂项目管理及跨产品数据整合。
- 当前规模边界：已验证 500 标签导入与搜索、100 标签原生恢复；不等同于验证 50,000 标签性能。导入仍限 25 MB / 50,000 标签，大型资料库可按会话导出。持续积累下的超大备份分卷与性能优化应另立任务。
